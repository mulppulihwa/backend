## 1. 정책 진단 — "시골/도시" 질문으로 축소 + 매칭 조정

> 회의 메모: "시골/도시로 질문 축소 -> 매칭도 살짝 수정(이전에는 지역마다 코드로 분류했었음)"
> "둘러보기 끝나고 진단현황 페이지에서 사용처랑 목록 볼 수 있다고 버튼 띄워주기"
> "기/디) 피그마 수정 - 프) 1,2 수정 - 백) 필드 수정"

### 현황

- 진단 폼(`Step1.jsx`) 2페이지에서 거주지 관련 질문이 4개나 있음:
  - "현재 어디 사세요?" (옥천/옥천 외) → `region_code` (REGION_CODES 매핑, 옥천군=`4329`)
  - "옥천군으로 언제 이사 오셨나요?" → `move_in_date`
  - "이전 거주지는 어디인가요?" → 카카오 Postcode 팝업으로 주소 검색 →
    `bname1`이 읍/면으로 끝나면 `읍면`, 아니면 `동`으로 자동 분류 → `prev_residence_type`
  - "이전 거주지에서 언제부터 거주하셨나요?" (백엔드 미저장, 프론트 로컬 표시용)
- `UserProfile.prev_residence_type` (`apps/users/models.py:53`, choices `동`/`읍면`)은 이미
  존재하며, `policy_matcher.py:96-97`에서 다음 규칙으로 사용 중:
  > 읍/면(이미 농촌 거주) 출신은 도시→농촌 이주를 전제로 하는 귀농 정책 제외
- `region_code`는 최근 커밋(`2c6829b`)에서 `profile_completed` 필수 항목에서 이미 제외됨.
- `region_code`는 `policy_matcher.py:27-30`의 `get_ancestor_codes()` → `region_codes__overlap`
  필터에 쓰이지만, §2(정책 DB 축소)로 정책 풀이 충북/옥천 위주가 되면 대부분의 정책이
  `region_codes=[]`(전국) 또는 충북/옥천을 포함해 이 필터의 변별력이 거의 사라짐.

### 결정 완료 (2026-06-14)

(A) "이전 거주지가 도시였는지 농촌이었는지"로 해석 확정. 다만 기존
`prev_residence_type`(choices `동`/`읍면`)을 그대로 재사용하지 않고
**boolean 필드로 전환**한다 (예: `prev_residence_is_rural`). 주소 검색 팝업 +
bname1 자동분류는 없애고 "예전에 사시던 곳은 도시였나요 농촌이었나요?" 2지선다
질문으로 대체.

추가로 region 계층 기반 매칭(`get_ancestor_codes` + `region_codes__overlap`,
`policy_matcher.py:21-30,67-72`)은 **제거**하기로 결정. 향후 크롤링 소스가
그린대로/옥천군청으로 한정되어 정책 풀 자체가 옥천 대상으로 보장되므로 region
계층 비교가 더 이상 필요 없음. `region_codes`/`Region` 모델/`UserProfile.region_code`
필드 자체는 삭제하지 않고 메타데이터로 유지.

구체적인 작업 순서와 사전 조사 결과는 **§9** 참고.

### "사용처/목록 보기" 버튼 (진단현황 페이지)

버튼 자체는 프론트 UI지만, 클릭 시 보여줄 "사용처 목록"이 **매칭된 정책의
`subsidy_tags`와 연관된 장소만 필터링**해야 한다면 `LocalPlace` 목록 API에
쿼리 파라미터 필터가 필요하다.

- `apps/places/views.py` `PlaceListView`에 `?subsidy_tags=` 쿼리 파라미터 추가:
  ```python
  class PlaceListView(APIView):
      def get(self, request):
          places = LocalPlace.objects.filter(is_active=True)
          tags = request.query_params.getlist('subsidy_tags')
          if tags:
              places = places.filter(subsidy_tags__overlap=tags)
          return Response(LocalPlaceSerializer(places.order_by('name'), many=True).data)
  ```
- 단순히 "사용처 지도로 이동" 버튼이라면 백엔드 변경 불필요.

## 2. 정책 DB — 수/범위 축소 (충북·옥천, 귀농귀촌)

> 회의 메모: "정책 수/범위 줄이기 - 백" / "이후에 찾아보고 우리가 노가다로
> 부연설명 필요하면 넣기 - 백" / "정책 수 줄이기 (충북옥천, 귀농귀촌)"

### 작업

- 스키마 변경 없음. `Policy.is_active`를 활용한 **데이터 정리 작업**.
- 선별 기준(제안): `region_codes`가 충북(`43`)/옥천(`43720`) 또는 전국(`[]`)이
  아니거나, `occupation_tags`에 `귀농`/`귀촌` 관련 태그가 없는 정책을 비활성화.
- `apps/policies/management/commands/`에 1회성 management command 작성 권장
  (기존 `apps/policies/management/` 디렉토리 존재 — 복지로 동기화 커맨드와 동일 패턴):
  ```python
  # apps/policies/management/commands/prune_policy_scope.py
  class Command(BaseCommand):
      help = '충북/옥천·귀농귀촌 범위 밖 정책을 비활성화한다 (v2.0.0 현장 피드백)'
      def add_arguments(self, parser):
          parser.add_argument('--dry-run', action='store_true')
      def handle(self, *args, **opts):
          # region_codes overlap 충북/옥천/전국 아니고
          # occupation_tags에 귀농/귀촌 계열 태그 없는 is_active=True 정책 조회
          # --dry-run이면 목록만 출력, 아니면 is_active=False 일괄 업데이트
  ```
- "노가다 부연설명"(`Policy.description`)은 기존 필드(이미 `TextField(blank=True)`,
  `PolicyDetailSerializer`에 포함됨) 그대로 사용 — **스키마 변경 불필요**, Django
  Admin에서 수동 입력.

### 영향

- §3(매칭 속도)·§8(홈 진행중인 정책)의 응답 속도/품질이 함께 개선됨.
- `FALLBACK_LIMIT = 10`(`policy_matcher.py:13`)은 줄어든 정책 풀에서도 fallback이
  자연스럽게 동작하므로 변경 불필요.

## 3. 정책 매칭 — 로딩 화면

> 회의 메모: "매칭 너무 오래걸림. 로딩 기다리는 이미지 필요" /
> "프) 기존에 있었던 로딩화면처럼 구성하되 피그마에 수정된 것 반영"

### 결론: 백엔드 코드 변경 없음

- 프론트 작업(`/loading` 화면, 기존 컴포넌트 재활용 + Figma 반영)이 핵심.
- `policy_matcher.py`의 매칭 자체는 SQL 1차 필터 후 Python에서 `condition_tree`만
  평가하는 가벼운 구조 — 느림의 원인은 대부분 **정책 row 수**(§2로 축소되면 개선)
  또는 Railway 무료 티어 cold start(배포 환경 이슈, 코드 범위 밖)일 가능성이 큼.
- §9에서 region 계층 매칭(`get_ancestor_codes`)을 제거해 매칭 쿼리가 한층 가벼워짐.
- §2 적용 후에도 체감 속도가 개선되지 않으면 추가 검토 항목(낮은 우선순위):
  - `PolicyMatchView` 응답을 사용자 프로필 해시 기준으로 짧게 캐싱

## 4. 정책 상세 — 상세정보 추가 (출처 링크, 게시일)

> 회의 메모: "정책 상세정보 더 추가. - 정보 출처로 가는 하이퍼링크(or 경로),
> 언제 업로드 되었는지 - 링크 얼마나 자세히 끌어올수잇는지 보고 하/경 결정"

### 현황

- `Policy.source_url` (URLField, blank=True)이 이미 존재하고
  `PolicyDetailSerializer`(`apps/policies/serializers.py:15-23`)에 포함되어 있음
  → "정보 출처 하이퍼링크"는 **필드 추가 불필요**, 데이터(노가다 입력) 문제일 가능성.
- "언제 업로드 되었는지"는 두 가지로 해석 가능:
  - `created_at`/`updated_at`(우리 DB에 저장된 시점) — 이미 존재하나
    `PolicyDetailSerializer`에 미포함.
  - 원문 공고가 실제 게시/공고된 날짜 — **신규 필드 필요** (현재 없음).

### 결정 필요

"링크 얼마나 자세히 끌어올 수 있는지" — `source_url`이 소스별로 다음 중 어디를
가리킬지에 따라 데이터 입력 방식이 달라짐:
- 복지로(`source='복지로'`): `apply_url`(상세조회URL)과 동일한 경우가 많음
- 귀농센터/수동입력: 원문 공고 페이지 또는 PDF 링크 — 건별 확인 필요

→ 확정 전까지는 아래 **2번**(게시일 필드)만 선행 가능.

### 작업

1. `Policy.published_at` (또는 `announced_at`) `DateField(null=True, blank=True)` 추가
   — 원문 공고 게시일.
   - 마이그레이션: `apps/policies/migrations/000X_policy_published_at.py`
   - `PolicyDetailSerializer.fields`에 `published_at`, `source_url`, `updated_at` 추가
2. `lib/parsing/policy_parser.py`의 `PARSE_TOOL`/`ParsedPolicy`에 `published_at`
   추출 필드 추가 검토 (공고문에 게시일이 명시된 경우 자동 채움, 없으면 수동 입력).
3. 기존 정책 데이터: `source_url`/`published_at` 비어있는 건 §2 축소 작업과 함께
   수동 보강(노가다).

## 6. 준비물(체크리스트) — 3단계 구조화

> 회의 메모: "3단계로 수정(우선순위 낮음 - 1단계는 주민등록증, 3단계가
> 주민센터 방문이고 2단계가 정책마다 다른거) 튜토리얼 느낌으로 -
> 백이 하고 대충 디자인하고 나서 수정"

### 현황

- `ChecklistItem` 모델(`apps/policies/models.py:62-69`): `policy` FK, `order`, `label`.
  AI 파싱(`lib/parsing/checklist_parser.py`)으로 정책별 생성.
- `GET /api/policies/<id>/checklist/` (`PolicyChecklistView`)가 평탄한 리스트 반환,
  24시간 캐시(`CHECKLIST_CACHE_TTL`).
- `PATCH /api/auth/policies/<id>/checklist/` (`UserPolicyChecklistView`)가
  `ChecklistItem.id` 기준으로 `UserPolicy.checked_items` 갱신.

### 작업 (1차 — 대충 구현, 추후 디자인 반영해 보정)

1. `ChecklistItem`에 `step = models.SmallIntegerField(default=2)` 추가 — 마이그레이션.
   - 기존 데이터/AI 파싱 결과는 모두 `step=2`(정책별 준비물)로 유지.
2. 1단계("주민등록증")·3단계("주민센터 방문")는 **DB에 저장하지 않고** 응답 시
   상수로 합성 (정책마다 동일하므로 DB 행 불필요):
   ```python
   # apps/policies/views.py 또는 신규 lib/checklist_steps.py
   FIXED_CHECKLIST_STEPS = {
       1: {'title': '신분증 준비', 'items': [{'label': '주민등록증'}]},
       3: {'title': '신청 접수', 'items': [{'label': '주민센터 방문'}]},
   }
   ```
3. `PolicyChecklistView` 응답을 3단계 구조로 변경:
   ```json
   {
     "steps": [
       {"step": 1, "title": "신분증 준비", "items": [{"label": "주민등록증"}]},
       {"step": 2, "title": "정책별 준비물", "items": [{"id": 12, "order": 0, "label": "..."}]},
       {"step": 3, "title": "신청 접수", "items": [{"label": "주민센터 방문"}]}
     ]
   }
   ```
   ⚠️ 기존 평탄 리스트 응답을 사용하는 프론트와 **호환되지 않는 변경** — 프론트
   작업과 함께 배포 필요.
4. `ChecklistItemSerializer`에 `step` 필드 추가.
5. `UserPolicyChecklistView`(체크 상태)는 1차에서 **2단계(ChecklistItem) 항목만
   체크 가능**하도록 유지 — 1/3단계는 고정 항목이라 `id`가 없어 체크 불가.
   체크리스트 진행률 계산에 1/3단계를 포함할지는 추후 디자인 확정 후 결정.

### 결정 필요

- 1/3단계 항목도 사용자가 체크할 수 있어야 하는지 (진행률 계산 포함 여부).
  → 필요해지면 정책별로 `ChecklistItem(step=1/3)` 행을 자동 생성하는 방식으로 전환.

### 좌표(lat/lng) — 등록 즉시 지도 노출 (구현 완료, 2026-06-15)

Daum Postcode는 좌표를 주지 않지만, 등록 즉시 카카오맵에 마커가 보이려면 `lat`/`lng`이
필요함. **프론트 우선 + 백엔드 폴백** 구조로 결정:

- `KAKAO_LOCAL_API_KEY`(REST API 키)는 현재 프론트가 관리 중 → 백엔드 `.env`에
  미설정 상태. `lib/services/geocoding.py`의 `geocode_address()`는 키가 없으면
  네트워크 호출 없이 `None`을 반환(안전한 폴백).
- `LocalPlaceWriteSerializer`(`apps/places/serializers.py`)에 `lat`/`lng`을 선택
  필드로 추가 — **프론트가 Kakao Maps JS SDK의 Geocoder로 변환한 좌표를 등록/수정
  요청에 함께 보내는 것을 1순위**로 처리.
- `lat`/`lng`이 같이 오지 않으면 `apps/places/views.py`에서 `geocode_address(address)`
  폴백 호출 (REST API 키가 추후 backend `.env`에 추가되면 자동으로 동작하게 됨).
- `PATCH`에서 `address`가 바뀌었는데 `lat`/`lng`을 같이 안 보낸 경우에만 백엔드가
  재geocoding — 클라이언트가 좌표를 같이 보내면 그 값을 그대로 사용.

### 신규 API

```python
# apps/places/urls.py
urlpatterns = [
    path('', PlaceListView.as_view()),               # GET 목록, POST 등록
    path('<int:pk>/', PlaceDetailView.as_view()),    # GET 상세, PATCH 수정, DELETE 삭제
]
```

- `GET /api/places/` — 목록. 시나리오 4번(본인 등록 사용처 카드에 수정/삭제 버튼)
  때문에 **목록 응답에도** `is_owner`(bool) 포함 필요 — 비로그인/타인 등록 항목은
  항상 `false`.
- `POST /api/places/` 🔒 — 사용처 등록 (`IsAuthenticated`). `created_by=request.user`
  자동 설정. 필수: `name`, `address`, `category`. 선택: `phone`, `business_hours`,
  `local_memo`, `lat`, `lng`(프론트 Geocoder 결과 — 없으면 백엔드 geocoding 폴백).
- `GET /api/places/<id>/` — 상세 조회 (수정 화면 프리필용). `is_owner` 포함.
- `PATCH /api/places/<id>/` 🔒 — 수정. 등록과 동일한 필드 집합. `created_by !=
  request.user`면 403.
- `DELETE /api/places/<id>/` 🔒 — 삭제. soft delete(`is_active=False`). 본인 아니면
  403. 삭제 확인 팝업은 프론트 책임 — 백엔드는 호출 즉시 처리.

### 권한/시리얼라이저

- `LocalPlaceSerializer`에 `business_hours`, `local_memo`, `is_owner`
  (`SerializerMethodField`, `request.user == created_by`) 추가. `created_by`는
  응답에 ID 노출하지 않고 `is_owner`로만 판별(개인정보 최소화).
- 등록/수정용 입력 시리얼라이저(`LocalPlaceWriteSerializer` 등)는
  `name`/`address`/`category`(필수), `phone`/`business_hours`/`local_memo`(선택)만
  허용 — `subsidy_tags` 등 관리자 전용 필드는 쓰기 막음.
- 카테고리 드롭다운: 기존 `CATEGORIES`(13개, `apps/places/models.py:7-12`) 그대로 사용
  — 추가 불필요.
- 별도 "내가 등록한 사용처" 목록 페이지는 만들지 않음 (회의 메모 "귀찮음") — 목록의
  `is_owner` + 카드 내 수정/삭제 버튼으로 대체.

## 8. 홈 화면 — "진행중인 정책" 통합 (진단 + 신청중, 최대 3개, 마감순)

> 회의 메모: "진단받은정책이랑 신청 진행중을 합쳐서 진행중인 정책 3개 정도만
> 표시 - 마감순 표시" / "화면 사이즈 딱 맞춰서 스크롤되지 않도록" /
> "프) 1번 현재 진단 받은 정책 에 안의 내용은 목록형으로"

### 현황

- 현재 `Home.jsx`는 `fetchSavedPolicies()`(`GET /api/auth/policies/` →
  `UserPolicyListView`, `-created_at` 정렬)만 호출해 상태가
  `신청완료`/`신청예정`인 것 중 마감 임박 **1건**만 "신청 진행 중"으로 표시.
- "진단받은 정책"(로그인 사용자의 `/api/policies/match/` 결과 중 아직 `UserPolicy`로
  저장 안 된 것)은 홈에서 별도로 노출되지 않음.

### 작업

신규 엔드포인트 추가 — 매칭 결과와 저장된 정책을 병합해 마감순 최대 3개 반환.

```python
# apps/policies/urls.py
path('in-progress/', PolicyInProgressView.as_view()),  # GET /api/policies/in-progress/ 🔒
```

```python
# apps/policies/views.py
class PolicyInProgressView(APIView):
    """홈 화면 '진행중인 정책' — 진단(매칭) + 신청중 저장 정책 병합, 마감순 최대 3개."""
    permission_classes = [IsAuthenticated]

    def get(self, request):
        profile = request.user.profile  # ProfileView와 동일하게 미작성 시 404 처리

        # 1. 저장된 정책 중 진행중(신청예정/신청완료)
        saved = (
            UserPolicy.objects
            .filter(profile=profile, status__in=[UserPolicy.Status.PENDING, UserPolicy.Status.APPLIED])
            .select_related('policy')
        )
        saved_policy_ids = {up.policy_id for up in saved}

        # 2. 매칭된 정책 중 아직 저장 안 된 것 ("진단받은 정책")
        match_result = match_policies(_build_profile_dict(profile))
        diagnosed = [p for p in match_result['policies'] if p.id not in saved_policy_ids]

        # 3. 병합 + 마감순(마감일 없으면 뒤로) + 최대 3개
        merged = [
            {'policy': up.policy, 'status': up.status, 'source': 'saved'} for up in saved
        ] + [
            {'policy': p, 'status': None, 'source': 'diagnosed'} for p in diagnosed
        ]
        today = timezone.now().date()
        merged.sort(key=lambda m: (
            0, (m['policy'].apply_end_date - today).days
        ) if m['policy'].apply_end_date else (1, 0))
        merged = merged[:3]
```

- 응답 형식(제안):
  ```json
  {
    "policies": [
      {
        "id": 12, "title": "...", "amount_text": "...", "benefit_type": "...",
        "apply_end_date": "2026-07-01", "days_left": 17,
        "status": "신청예정",      // null이면 "진단됨"(아직 미저장)
        "source": "saved"          // "saved" | "diagnosed"
      }
    ],
    "total": 3
  }
  ```

- `status`/`source`로 프론트가 카드 뱃지(신청완료/신청예정/진단됨)를 구분 표시.
- "최대 3개"를 백엔드에서 강제 → 프론트는 화면 크기에 맞춘 고정 레이아웃 구성 가능
  (스크롤 불필요 요건은 프론트 CSS 작업).
- 기존 `/api/policies/match/`, `/api/auth/policies/` 엔드포인트는 그대로 유지
  (전체 목록 페이지 등에서 계속 사용).

## 9. 작업 순서 — 정책 진단·매칭 로직 수정

> §1에서 확정된 두 가지 변경(`prev_residence_type` boolean 전환, region 계층
> 매칭 제거)을 실제로 적용할 때의 작업 순서. 오류 발생 가능성이 낮은 순서로 배치.

### 사전 조사 결과 (2026-06-14, 운영 DB 기준)

- `Policy` 총 1,420건 — `복지로` 1,400건(`is_active=True` 94건,
  그중 1,399건이 `region_codes=[]`), `수동입력` 20건(전부 `region_codes`가
  충북`["43"]`/옥천`["43720"]`).
- `region_codes=[]`인 정책은 현재 매칭 로직에서도 region 필터를 무조건 통과함
  → region 계층 매칭 제거가 복지로 정책의 노출 범위를 바꾸지 않음(기존에도
  전국 노출 상태였음).
- `User` 13명 / `UserProfile` 13건 / `UserPolicy` 125건(신청예정 109,
  신청완료 11, 관심없음 5) — 그중 35건이 `복지로`+`is_active=True` 정책에 연결.
- → 7번(계정 초기화)을 최종 단계로 계획해, 1번·6번 작업에서 기존
  유저/정책 데이터의 마이그레이션·cascade를 신경 쓰지 않아도 되도록 함.

### 작업 순서

1. **유저 필드 수정** — `apps/users/models.py`의 `PREV_RESIDENCE_CHOICES`(동/읍면)
   → boolean 필드(예: `prev_residence_is_rural`)로 전환, 마이그레이션 추가.
   - `policy_matcher.py:96-97`의 `prev_residence_type == '읍면'` 참조와
     `_build_profile_dict()`(`apps/policies/views.py`)의 키를 **같은 작업으로
     동시 수정** — 분리하면 중간 상태에서 매칭이 깨짐.
   - 기존 13개 `UserProfile`의 `prev_residence_type` 값 마이그레이션은 불필요
     (7번에서 계정 초기화 후 재가입 시 새로 입력).
2. **정책 필드 수정** — §4의 `Policy.published_at` 등 신규 필드 추가
   (additive, 마이그레이션만 — 기존 row는 default로 채워짐, wipe 불필요).
3. **정책 매칭로직 설계** — `policy_matcher.py`에서 `get_ancestor_codes` 호출과
   region 필터 블록(21-30행, 67-72행) 제거, `lib/matching/region_hierarchy.py`
   의존 제거, `tests/test_policy_matcher.py`에서 관련 테스트 정리.
4. **정책 크롤링 source 수정** — 그린대로/옥천군청 어댑터를
   `lib/sync/adapters/`에 추가 (`bokjiro_sync.py`의 `update_or_create` upsert
   패턴 재사용), `Policy.SOURCES`에 choice 추가, 2번에서 추가한 필드를 채우도록
   구현.
5. **샘플 데이터 테스트** — 새 크롤러로 소량 수집 후 매칭 로직 전체 플로우
   검증(운영 DB 미변경, `--dry-run`/`--max-items` 활용).
6. **정책 DB 정리 + 전체 크롤링** — 검증 통과 후 §2의 `prune_policy_scope`로
   복지로 비옥천 정책 정리, 그린대로/옥천군청 전체 크롤링 실행.
7. **계정 초기화 (최종 단계)** — `User`/`UserProfile`/`UserPolicy` 전체 삭제
   (cascade), 기존 13명 유저에게 재가입 안내. v2.0.0의 모든 변경(§1~8) 배포·검증
   완료 후 마지막에 실행.
